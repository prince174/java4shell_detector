# java4shell_detector

В GUI по умолчанию выбран профиль **Java4Shell · CVE-2026-114938**. Он ищет Java 17 от 17.0.6, ветки 21, 25 и 27, Oracle Java 8 Performance и Oracle GraalVM Enterprise Edition 21.3.20.0.3. Для распознанных сборок Oracle Java SE профиль учитывает исправленные базовые версии 8u513, 17.0.21.1, 21.0.13.1, 25.0.5.1 и 27.0.1.1. Для других поставщиков кандидат требует сверки сборки с их бюллетенем. Для CLI профиль включается флагом `--profile java4shell`. [Матрица Oracle](https://www.oracle.com/security-alerts/cspunov2026.html#AppendixJAVA) · [Версии исправлений Oracle](https://www.oracle.com/java/technologies/javase/27-0-1-1-relnotes.html) · [Исследование Upwind](https://www.upwind.io/blog/java4shell-what-we-know-now-and-what-comes-next)

Чтобы выбрать свои ветки, открой профиль **Выбранные версии Java** и введи список в поле **Мажорные версии Java**. В этом режиме по умолчанию выбрана ветка 17 с порогом **17.0.6 включительно**. Обозначение `17` без номера обновления получает `unknown_version`.

## Запуск

Для запуска на Linux и macOS требуется Docker с Compose 2.30+ для чтения `env_file` в режиме `raw`. Выполни из корня проекта:

```sh
test -f .env || cp .env.example .env
# Укажи реальные адреса и учётные данные в .env.
docker compose up -d --build --wait
```

Открой [веб-интерфейс](http://localhost:8080). Порт задаёт `JAVA4SHELL_PORT`. После изменения `.env` выполни `docker compose up -d --force-recreate`. Compose публикует интерфейс на loopback. Отчёты сохраняются в `reports/` на хосте. Веб-интерфейс показывает состояние и ссылки последнего запуска каждого источника с момента запуска сервиса.

При обновлении с версии, где сервис Compose назывался `inventory`, замени ключ сервиса в локальном `compose.override.yaml`, если он используется. Затем выполни `docker compose up -d --build --remove-orphans --wait`, чтобы удалить старый контейнер Compose и освободить порт. Отчёты загружаются из каталога `reports/`.

### Подключения

| Источник | Параметры в `.env` |
| --- | --- |
| Bitbucket Data Center | `BITBUCKET_URL` с контекстным путём, если он используется, и `BITBUCKET_TOKEN` с правом чтения репозиториев |
| Bitbucket Cloud | `BITBUCKET_CLOUD_WORKSPACE`, `BITBUCKET_CLOUD_EMAIL` и `BITBUCKET_CLOUD_TOKEN` для API token. Для Bearer access token email оставь пустым |
| Nexus REST | `NEXUS_URL` и `NEXUS_REST_USERNAME`/`NEXUS_REST_PASSWORD` для Basic или `NEXUS_TOKEN` для Bearer при поддержке на стороне сервера |
| Nexus Docker Registry | На хосте из `NEXUS_URL` используются `NEXUS_REST_USERNAME`/`NEXUS_REST_PASSWORD`. Для отдельной учётной записи или Registry на другом хосте задай `NEXUS_DOCKER_USERNAME`/`NEXUS_DOCKER_PASSWORD` |

Для GUI платформа выбирается в форме. В CLI исходный режим задаёт `BITBUCKET_PROVIDER` или флаг `--provider`. Значения секретов остаются в окружении сервиса. Формат Compose `raw` сохраняет специальные символы, включая `$`. В `.env` записывай значения без кавычек. Для защищённых корпоративных сервисов используй HTTPS и доверенный сертификат. Переменные `BITBUCKET_ALLOW_HTTP_AUTH=1` и `NEXUS_ALLOW_HTTP_AUTH=1` разрешают аутентификацию по HTTP для изолированного стенда.

Для маршрутизации по пути достаточно `NEXUS_URL=https://nexus.example.com`. Сканер построит ссылку вида `nexus.example.com/docker-hosted/team/app:1.0` для каждого репозитория автоматически. Для репозитория с выделенным Docker-портом или отдельным хостом можно указать исключение в `NEXUS_REGISTRIES`, например `{"docker-hosted":"https://docker.example.com:18443"}`. Для Docker-групп указывай имена отдельных репозиториев-участников. При развёртывании в контейнере `localhost` указывает на сам контейнер. Для опубликованных на Docker Desktop тестовых портов используй `host.docker.internal`.

Чтобы сузить опрос Nexus, введи точные имена репозиториев в поле **Docker-репозитории**, например `java4shell-fixtures` или `docker-prod,docker-stage`. Имена видны в **Nexus → Browse**. В CLI укажи один `--repository` на каждое имя.

Во вкладках **Репозитории Bitbucket** и **Образы Nexus** показывается последний сохранённый отчёт по 10 репозиториев или образов на страницу. В Bitbucket по проектам сгруппированы только репозитории-кандидаты. Для каждого показаны версия Java, причина отбора и ссылка на строку первого совпадения. На вкладке Nexus флажок **Только кандидаты** фильтрует образы. Для ссылок на публичный адрес reverse proxy можно задать `BITBUCKET_WEB_URL` для Data Center и `NEXUS_WEB_URL`.

## Сборка через корпоративный Nexus

Положи сертификаты корпоративного CA в `certs/` как PEM-файлы с расширением `.crt`, по одному сертификату в файле. Dockerfile добавляет их в системное хранилище доверия этапа `crane` перед скачиванием Go-модулей и итогового образа перед запуском Python и `crane`. Каталог может быть пустым. После замены CA пересобери сервис командой `docker compose up -d --build --wait`. Git игнорирует локальные сертификаты.

В `.env` можно указать Go proxy и прокси базы контрольных сумм. Compose передаёт значения на этап `go install`. Пустые параметры используют стандартные настройки Go.

```dotenv
GOPROXY=https://nexus.example.com/repository/go-proxy/
GOSUMDB=sum.golang.org https://nexus.example.com/repository/go-sumdb/
```

Базовые образы заданы в двух строках `FROM` Dockerfile. Если они тоже должны скачиваться из Nexus, укажи там полные ссылки на образы из Docker-репозитория. Укажи только адрес Nexus в `GOPROXY`, если Go-модули должны скачиваться через него без прямого доступа. Передавай учётные данные для загрузки образов через `docker login`. Если Go proxy требует аутентификации, используй секрет BuildKit для `.netrc`. URL в build args предназначены для адресов без паролей и токенов.

Если корпоративный CA требуется уже при загрузке базовых образов из `FROM`, добавь его также в доверенные сертификаты Docker Desktop или BuildKit. Docker загружает эти образы до выполнения команд Dockerfile. [Docker и CA](https://docs.docker.com/engine/network/ca-certs/) · [Настройка Go в Nexus](https://help.sonatype.com/en/configure-go-with-nexus.html)

## Как проходит опрос

GUI передаёт фильтры, профиль Java и задержку локальному Python API. Одновременно может идти один опрос Bitbucket и один опрос Nexus. Сканер Bitbucket ищет объявления Java в исходных конфигурациях, а сканер Nexus проверяет JVM в файловой системе опубликованных образов.

### Bitbucket Cloud и Data Center

1. **Получает каталог репозиториев.** Для Data Center читает страницы `GET /rest/api/latest/repos`, для Cloud — `GET /2.0/repositories/{workspace}`. Пустое поле «Проекты» включает все репозитории, доступные учётной записи в выбранной области. Если указать ключи проектов, сканер отфильтрует каталог до клонирования.
2. **Получает снимок репозитория.** Один неглубокий `git clone --depth 1` на репозиторий загружает доступные для опроса вершины веток без checkout. Git может выполнить несколько сетевых запросов в рамках клонирования. По умолчанию используется последний коммит основной ветки. Если заданы дополнительные шаблоны, например `release/*`, сканер начинает с основной ветки и продолжает подходящими ветками в порядке имён.
3. **Читает выбранные файлы из локального Git.** `git ls-tree` перечисляет файлы коммита, а `git cat-file` читает содержимое подходящих файлов. Сканер обрабатывает обычные файлы, включая исполняемые, и проверяет размер перед чтением. Совпадающие коммиты пропускаются. Один и тот же путь с тем же Git blob проверяется один раз за опрос репозитория, а изменившееся содержимое проверяется снова.
4. **Классифицирует находки по выбранному профилю.** Сканер проверяет все выбранные версии Java в одном проходе. При первом совпадении со статусом `candidate` он сохраняет строку, файл, ветку, коммит, обнаруженную версию и её мажор (`java_major`), закрывает временный клон и переходит к следующему репозиторию. Кандидат в основной ветке завершает опрос до анализа дополнительных веток.

| Что читается | Что распознаётся | Зачем |
| --- | --- | --- |
| `Dockerfile*`, `Containerfile*`, `*.dockerfile`, `*.containerfile` | Java в тегах `FROM`, например `eclipse-temurin:21-jdk-noble` и `gradle:8.14.3-jdk17`. Подставляются значения `ARG` перед первым `FROM`. Читаются объявления `ENV JAVA_VERSION` и `ENV JDK_VERSION`. | `runtime_base` обозначает базовый образ финального этапа, а `intermediate_base` — базу промежуточного. Прямая копия каталога `jdk`, `openjdk` или `jre` из этапа по имени или номеру в финальный через обычный или JSON-синтаксис `COPY --from` даёт роль `bundled_jdk`. При нескольких источниках проверяется каждый исходный путь. |
| `pom.xml` | `java.version`, `jdk.version`, свойства компилятора, теги `release`, `source`, `target`, `jdk` и ссылки на свойства, объявленные в том же POM. XML-комментарии пропускаются. Для многострочных значений ссылка ведёт к открывающему тегу. | `build_jdk_declaration` указывает декларацию JDK сборки. `bytecode_target` показывает настройки целевой версии компиляции. |
| `*.gradle`, `*.gradle.kts`, `gradle.properties` | `JavaLanguageVersion.of(...)`, `jvmToolchain(...)`, `sourceCompatibility`, `targetCompatibility`, `options.release.set(21)`, `options.release = 21`, `org.gradle.java.home`, `jvmTarget`, `kotlinOptions { jvmTarget = "21" }` (также одинарные кавычки), `jvmTarget.set(JvmTarget.JVM_21)`, `jvmTarget = JvmTarget.JVM_21` (включая полное имя enum и legacy `JVM_1_8`), `jvmTarget.set(JvmTarget.fromTarget("21"))` и распознаваемые объявления версии Java/JDK. | Показывает выбранный JDK сборки или цель компиляции в зависимости от найденной настройки. В Gradle пропускаются комментарии `//` и `/* ... */`, с сохранением номеров строк и строковых значений. |
| `Jenkinsfile*`, `*.yaml`, `*.yml` | Jenkins `jdk` (комментарии `//` и `/* ... */` пропускаются с сохранением номеров строк), объявления версии JDK в CI и ссылки `image:` на Java-образы в YAML. | Показывает объявленную Java в сборочной среде или версию по тегу образа (`image_reference`). |
| `.java-version`, `.tool-versions`, `.sdkmanrc` | Версия Java в файлах выбора инструментария. В `.tool-versions` проверяются все варианты в строке `java` до комментария. | Показывает, какой JDK задан в конфигурации проекта. |

Например, `<release>21</release>` задаёт цель компиляции. `FROM eclipse-temurin:21-jdk-noble` указывает ветку Java в базовом образе. В обоих случаях точная сборка JVM в опубликованном образе определяется отдельным опросом Nexus. Bitbucket читает декларации статически. Внешние родительские POM, динамические CI-шаблоны и установка Java произвольными shell-командами могут потребовать отдельной проверки.

### Docker-образы в Nexus

1. **Получает каталог репозиториев.** В режиме `NEXUS_DISCOVERY=auto` сканер начинает с `GET /service/rest/v1/repositories`. При таймауте или HTTP 403, 404, 405 он получает каталог через `coreui_Repository.readReferences` на `POST /service/extdirect`. Режим `rest` требует успешного REST-запроса каталога. Режим `extdirect` сразу получает каталог через ExtDirect. До обхода образов проверяется структура каталога: массив записей с непустыми строками `name`, `format`, `type`. Некорректный ответ сохраняется как ошибка `list_repositories` с причиной; сканирование образов не начинается.
2. **Выбирает Docker-репозитории.** При пустом поле «Docker-репозитории» берёт доступные репозитории с `format=docker` и `type=hosted`. Флажок proxy добавляет закэшированные образы из Docker proxy. При явном списке проверяет указанные Docker hosted и proxy. Для группы нужно указать имена её участников.
3. **Перечисляет ссылки на образы.** После каталога сканер вызывает `POST /service/extdirect` с `coreui_Browse.read`, именем репозитория и узлом `v2`. Обходит дочерние папки, извлекает ссылки из `tags` и `manifests` и пропускает ветку `v2/blobs`. Этот шаг одинаков для всех режимов. Вызов `/service/rest/v1/assets` в маршруте отсутствует.
4. **Читает манифесты через Docker Registry.** Сканер строит ссылку вида `nexus.example.com/docker-hosted/team/app:1.0` или использует переопределение из `NEXUS_REGISTRIES`. Сначала обрабатывает теги. Команда `crane digest` получает дайджест тега, а `crane manifest` читает манифест по дайджесту. Если это индекс OCI или Docker, сканер раскрывает его платформенные манифесты и пропускает аттестации и артефакты. При необходимости читает платформу из `crane config`. Ошибка чтения одного платформенного манифеста сохраняется в отчёте, остальные продолжают проверяться.
5. **Экспортирует финальную файловую систему.** `crane export` сохраняет её во временный tar. Результат успешного анализа переиспользуется для того же дайджеста платформенного манифеста в текущем опросе. Отдельные теги сохраняются в отчёте. Ссылки по дайджесту, уже покрытые тегами того же образа, пропускаются, а нетегированные манифесты проверяются отдельно.
6. **Подтверждает наличие JVM по файлам.** Сканер читает tar последовательно и сопоставляет обычный файл `release` размером до 64 КиБ с признаками JVM в том же дереве JDK. Ищет `bin/java`, `bin/java.exe`, `libjvm.so`, `libjvm.dylib` и `jvm.dll`. Читает `JAVA_RUNTIME_VERSION`, а если поля нет — `JAVA_VERSION`. Поставщика берёт из `IMPLEMENTOR` или `JAVA_VENDOR`, версию GraalVM — из `GRAALVM_VERSION`, если она указана. Путь к `release` и найденные признаки JVM сохраняются как доказательства. При наличии JVM без подходящего `release` находка получает `unknown_version`. Содержимое образа анализируется без запуска контейнера или JVM.

### Статистика и результаты

- Задержка по умолчанию `0.1` секунды применяется между запросами GET и POST к API. В GUI видны количество запросов и ошибок, метод и путь последнего запроса, его статус, последнее, среднее и максимальное время. Для Git и Registry отдельно измеряются операции клонирования и команды `crane`. Эти клиенты управляют своими HTTP-запросами самостоятельно.
- `inventory.json` хранит область опроса, обработанные объекты, находки и ошибки охвата. `outside_scope` означает, что находка не прошла критерии профиля. `unknown_version` означает, что данных для классификации версии недостаточно. `candidates.csv` содержит только строки со статусом `candidate`.
- В Bitbucket свидетельство привязано к файлу, строке и коммиту. Во вкладке результатов показано первое совпадение на репозиторий. В Nexus находка привязана к тегу или дайджесту, платформе и пути внутри образа. Кандидат означает совпадение с критериями выбранного профиля. Метки вроде `21-jdk-noble` требуют сверки точной сборки и уровня обновления.
- Ошибка команды `crane` появляется в диагностике и DEBUG-журнале сразу после команды. Веб-отчёты сохраняются в `reports/<источник>/<id запуска>/`.

## CLI

CLI работает на Python 3.11+ без сторонних Python-пакетов. Для Bitbucket нужен `git` в PATH, для Nexus — `crane`. Оба входят в образ Compose. При сборке образа Git устанавливается из Debian APT, поэтому на стенде нужен доступ к настроенному зеркалу Debian.

```sh
python3 bitbucket_inventory.py --provider datacenter --project APP --branch 'release/*' --delay 0.1
python3 bitbucket_inventory.py --provider cloud --project J4S01 --delay 0.2
python3 nexus_inventory.py --repository java4shell-fixtures --java-majors 17,21,25,27 --delay 0.1
```

### Разовый запуск Nexus в контейнере

Из корня проекта выполни команду ниже. Compose соберёт образ и запустит одноразовый контейнер с `crane`.

```sh
docker compose run --build --rm --no-deps -T java4shell_detector \
  python nexus_inventory.py --repository java4shell-fixtures \
  --java-majors 17,21,25,27 --delay 0.1 --output /reports/nexus-cli
```

Замени `java4shell-fixtures` на имя нужного Docker-репозитория. JSON и CSV будут доступны в `reports/nexus-cli/` в рабочем каталоге. Код выхода `2` означает ошибки охвата. В этом случае сканер сохраняет частичные результаты.

### Опрос `aa-docker-prod` в TeamCity

В **Parameters** задай переменные окружения шага:

| Параметр | Значение |
| --- | --- |
| `env.NEXUS_URL` | Базовый URL Nexus, например `https://nexus.isb` |
| `env.NEXUS_REST_USERNAME` | Имя пользователя Nexus с правом чтения каталога и образов |
| `env.NEXUS_REST_PASSWORD` | Пароль Nexus, тип **Password** |

Добавь шаг **Command Line → Custom script** на агенте Linux или macOS с Docker Compose. Рабочий каталог шага — корень checkout.

```sh
sh scripts/teamcity-nexus-aa-docker-prod.sh "%system.teamcity.build.id%"
```

[Скрипт](scripts/teamcity-nexus-aa-docker-prod.sh) передаёт значения из окружения TeamCity в контейнер по имени переменной. Для Nexus API и Registry на том же хосте используется одна Basic-пара. Для запуска достаточно параметров TeamCity.

В **General Settings → Artifact paths** укажи два файла:

```text
reports/nexus-cli/%system.teamcity.build.id%/inventory.json => nexus
reports/nexus-cli/%system.teamcity.build.id%/candidates.csv => nexus
```

Установи **Publish artifacts → Always**. Сканер с ошибками охвата записывает JSON и CSV и завершает шаг с кодом `2`. TeamCity опубликует частичный отчёт в **Artifacts → nexus** даже при неуспешной сборке. Если ошибка произошла до запуска сканера, отчёты за этот билд ещё не созданы.

[Настройка шага TeamCity](https://www.jetbrains.com/help/teamcity/command-line.html) · [Публикация артефактов](https://www.jetbrains.com/help/teamcity/configuring-general-settings.html)

По умолчанию Bitbucket проверяет основную ветку. Для всех веток передай `--branch '*'`. Для Nexus можно передать `--include-proxy`. CLI возвращает код 2 при ошибках охвата и сохраняет доступные результаты. Опция `--progress` выводит события HTTP и операций Registry для мониторинга.

## Dependency-Track

JDK и JRE находятся вне дерева зависимостей Maven и Gradle. JVM может поставляться в базовом образе, устанавливаться системным пакетом или копироваться вместе с приложением. SBOM, построенный только по зависимостям приложения, описывает библиотеки и не даёт сведений о версии этой JVM. Поиск компонентов в таком SBOM не позволяет оценить охват Java4Shell.

Dependency-Track покажет JVM, если в него загружен SBOM финального образа или установленного продукта и инструмент инвентаризации перечислил сам JDK или JRE как компонент. Детектор проверяет файлы рантайма в финальном образе Nexus и сохраняет версию, путь и digest как доказательства.

## Проверка

Ошибки опроса отображаются в GUI под счётчиками запросов. Для логов Compose переменная `INVENTORY_LOG_LEVEL` в `.env` принимает `DEBUG` (по умолчанию), `INFO`, `WARNING`, `ERROR` или `CRITICAL`. На уровне `DEBUG` в логах видны запросы к API и операции `crane` с результатом и временем. Параметры URL, заголовки авторизации и тела ответов в трассировку не входят. После смены уровня пересоздай контейнер и смотри `docker compose logs -f --tail=10`. Код `202` для `POST /api/start/bitbucket` означает, что опрос принят. Его состояние и диагностику показывает `GET /api/status`.

```sh
python3 -m unittest discover -s tests -v
docker compose config --quiet
docker compose up -d --build --wait
python3 tests/check_live.py --url http://127.0.0.1:18084
```

Модульные и интеграционные тесты запускаются без токенов. Они проверяют границы версий, пагинацию и задержку REST на локальном Data Center API, режим Cloud на фикстурах, файлы рантайма, мультплатформенные манифесты и удаление дублей Nexus.

Для живого прогона скрипт обращается к уже запущенному сервису и скачивает оба отчёта через тот же API, что используется в GUI. В Bitbucket Cloud используются проекты `J4S01`–`J4S10` workspace `artifact_graph`. Docker-образы с настоящим Eclipse Temurin JRE загружены в `java4shell-fixtures` на локальном Nexus кластера `osa-nexus-e2e`. Ожидание для каждого источника — 10 находок, 8 кандидатов, 0 ошибок охвата. Пограничные проверки включают Java 17.0.5, Java 17.0.6 и Java 21.0.5.

При запуске с `--java-majors 17,21,25,27` ожидаются девять кандидатов на источник, поскольку в выборку также входит тестовая Java 21.0.5.

На локальном стенде веб-интерфейс опубликован на порту 18084. Nexus REST и Docker connector доступны контейнеру через `host.docker.internal` на портах 18182 и 18184, пока работают соответствующие port-forward. При исчерпании подсетей Docker Desktop локальный `compose.override.yaml` может задать `network_mode: bridge` для сервиса `java4shell_detector`.
